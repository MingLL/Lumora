# 微信公众号事件统计与邮件日报服务设计

## 目标

在 Lumora 中新建一个可独立部署的微信公众号纯后台服务。服务接收并持久化微信公众号事件，统计前一天的数据，并在每天北京时间 07:00 通过 QQ 邮箱发送日报。

第一版支持以下六类事件：

1. 关注和取消关注事件
2. 扫描带参数二维码事件
3. 上报地理位置事件
4. 自定义菜单事件
5. 点击菜单拉取消息事件
6. 点击菜单跳转链接事件

项目借鉴 FurtherWarmth 的 Java、Spring Boot、Weixin Java Tools、MyBatis 和 MySQL 技术路线，但不直接复制其历史实现。FurtherWarmth 中已注释的数据写入、分散的数据模型、硬编码敏感信息和缺失的测试不会带入新项目。

## 范围

### 包含

- 微信公众号服务器地址的 GET 验证
- 明文模式和安全模式的 POST 回调
- 六类事件的解析、归一化、幂等入库
- 昨日事件汇总和明细分组
- 每天 07:00 的 QQ SMTP 邮件日报
- 受密钥保护的手动补发接口
- MySQL 数据库迁移
- 健康检查、容器镜像、Compose 和 dev2 部署脚本
- 单元测试和数据库集成测试

### 不包含

- 网页管理后台
- 用户画像或关注者资料同步
- 实时告警和流式分析
- 消息队列和多服务拆分
- 精确位置在邮件中的展示
- 主动群发公众号消息

## 方案选择

采用在 Lumora 中新建干净 Spring Boot 服务的方案。

直接改造 FurtherWarmth 虽然初始改动较少，但会继承历史代码和安全问题。把接收与统计拆成两个服务具有更强的扩展能力，但第一版引入消息队列和分布式部署没有必要。单体服务足以覆盖当前流量和功能，同时通过模块边界保留将来拆分的可能。

## 系统架构

```text
微信公众号
    │ GET 验证 / POST 事件推送
    ▼
微信回调入口（验签、解密、解析）
    ▼
事件归一化与幂等写入
    ▼
MySQL
    │
    ├── 查询昨日统计
    ▼
日报调度器（每天 07:00 Asia/Shanghai）
    ▼
QQ SMTP
    ▼
配置的收件人
```

服务按职责分为以下模块：

- `wechat`：微信公众号配置、回调协议、验签、解密和事件转换。
- `event`：统一事件模型、幂等持久化和查询。
- `report`：统计口径、邮件内容生成、执行记录和补发。
- `mail`：QQ SMTP 适配。
- `operations`：健康检查、部署配置和运维接口保护。

模块之间使用明确的服务接口协作。控制器不直接执行 SQL，事件处理器不直接发送日报，调度器不负责组装数据库查询。

## 回调处理

### GET 验证

回调地址接收 `signature`、`timestamp`、`nonce` 和 `echostr`。服务通过公众号 Token 验证签名，仅在验证成功后原样返回 `echostr`。

### POST 事件

服务支持明文模式和安全模式。安全模式使用 `msg_signature`、`timestamp`、`nonce` 和 AES Key 验签解密。解密和 XML 解析使用 Weixin Java Tools 提供的能力，避免自行实现微信密码协议。

处理流程：

1. 验证请求签名。
2. 解密并解析 XML。
3. 将微信消息转换为统一事件。
4. 生成幂等键并尝试入库。
5. 成功或重复事件均返回微信要求的成功响应。

未知事件保存为 `UNKNOWN`，同时记录原始消息类型和事件名称。这样微信新增事件类型时，回调不会因为枚举转换失败而中断。

### 事件类型

内部事件类型至少包括：

- `SUBSCRIBE`
- `UNSUBSCRIBE`
- `SCAN`
- `LOCATION`
- `MENU_CLICK`
- `MENU_VIEW`
- `UNKNOWN`

关注时扫描带参数二维码仍记录为 `SUBSCRIBE`，同时保存 `qrscene_` 场景参数。已关注用户扫码记录为 `SCAN`。日报将二者都纳入二维码场景统计，但关注数只统计 `SUBSCRIBE`。

## 数据模型

### `wechat_event`

统一事件表包含：

- 自增主键
- 公众号 AppID
- OpenID
- 内部事件类型
- 微信消息类型和原始事件名称
- 微信消息 ID（存在时）
- 微信事件发生时间
- 幂等键
- 二维码场景参数和 Ticket
- 菜单 EventKey
- 菜单跳转 URL
- 纬度、经度和位置精度
- 原始 XML 的受控摘要
- 接收时间和创建时间

索引包括：

- `app_id + deduplication_key` 唯一索引
- `occurred_at + event_type` 统计索引
- `open_id + occurred_at` 用户去重索引

幂等键优先使用微信消息 ID。事件没有消息 ID 时，使用 AppID、OpenID、事件类型、微信发生时间和关键业务字段的稳定散列。数据库唯一索引是最终幂等保障。

原始 XML 默认不完整落库，只保存排查所需且经过长度限制的摘要。密钥、签名参数和邮件授权码不会落库或写入日志。

### `daily_report_execution`

日报执行表包含：

- 报告日期
- 状态：`RUNNING`、`SENT` 或 `FAILED`
- 尝试次数
- 收件人快照
- 开始时间、发送时间
- 最后失败原因的受限摘要

`report_date` 使用唯一索引，防止并发调度导致同一天重复发送。手动补发可显式覆盖失败记录；已成功日报默认拒绝重复发送，除非请求明确指定强制补发。

### 数据库迁移

Flyway 管理结构变更。首次启动自动创建表、索引和迁移历史，不依赖人工执行 SQL。

## 统计口径

调度器在每天北京时间 07:00 统计昨天 `00:00:00`（含）至今天 `00:00:00`（不含）的事件。数据库查询使用明确的 UTC 时间边界，应用以 `Asia/Shanghai` 计算报告日期，避免服务器时区不同造成跨日偏差。

日报包含：

- 总事件次数
- 总去重用户数
- 每类事件的次数和去重用户数
- 新增关注数
- 取消关注数
- 净增长
- 二维码场景参数分布
- 菜单 EventKey 分布
- 菜单跳转 URL 分布
- 地理位置上报次数
- 统计区间和报告生成时间

菜单类统计分别展示 `MENU_CLICK` 和 `MENU_VIEW`，并可在总览中合并为菜单交互。地理位置只汇总次数和去重用户数，不在邮件中展示用户精确坐标。

没有事件时仍发送成功日报，正文明确写明“昨日无事件”，用于证明定时任务和邮件链路正常。

## 邮件发送

邮件使用 Spring Mail 连接 QQ SMTP：

- 主机：`smtp.qq.com`
- 端口：`465`
- SSL：启用
- 用户名：`MAIL_USERNAME`
- 授权码：`MAIL_AUTH_CODE`
- 收件人：`REPORT_RECIPIENTS`，支持逗号分隔多个邮箱

邮件主题包含公众号标识和报告日期。正文使用兼容主流邮件客户端的简单 HTML，同时生成纯文本替代内容。

发送失败最多重试三次，使用有界退避。最终失败写入执行记录并输出不含凭据的结构化错误日志。下一次正常调度不会自动发送更早日期的失败日报，运维人员通过手动补发接口选择日期重试。

## 手动补发接口

提供内部运维接口，例如：

```text
POST /internal/reports/{date}/send
```

请求必须携带由环境变量配置的管理密钥。密钥使用常量时间比较，不输出到日志。接口校验日期不能是未来日期，并返回明确的执行结果。该接口不替代正式的用户认证系统，只用于受网络和密钥双重保护的运维操作。

## 错误处理和可观测性

- 签名失败返回 403，不进入业务处理。
- XML 无法解析返回 400，并记录不含原文敏感数据的请求标识。
- 数据库暂时不可用时返回非成功状态，使微信能够重试。
- 重复事件视为成功，不产生错误日志。
- 未知事件正常入库并记录告警级别指标。
- 邮件失败不影响回调处理。
- Spring Boot Actuator 提供存活和就绪检查。
- 日志使用结构化字段，包括事件类型、报告日期和跟踪标识，不记录 OpenID 全值；展示时进行掩码。

服务启动时校验微信公众号、数据库、邮件和内部管理密钥配置。缺失必要配置时快速失败，并明确指出配置项名称。

## 部署设计

构建使用多阶段 Dockerfile，运行镜像使用非 root 用户。`compose.yaml` 定义：

- Lumora 应用
- MySQL
- 持久化数据卷
- 健康检查
- 自动重启策略

应用仅暴露内部 HTTP 端口。dev2 上若已有 Nginx、Caddy 或其他入口，则复用现有反向代理提供公网 HTTPS；若没有，再单独补充入口配置。微信公众号后台需要配置一个微信服务器可访问的 HTTPS 回调地址。

部署脚本执行以下安全步骤：

1. 检查 dev2 的 Docker、Compose、端口和反向代理。
2. 上传或拉取确定版本的项目。
3. 校验服务器端 `.env` 必要配置。
4. 构建并启动容器。
5. 等待健康检查通过。
6. 验证本地回调健康端点。

脚本不创建或覆盖实际 `.env`，也不在命令输出中打印敏感值。部署失败保留旧容器和日志供排查，不执行破坏性清理。

## 安全说明

FurtherWarmth 的历史源码中存在硬编码的 OpenAI API Key。Lumora 不复制该代码或凭据。如果该 Key 仍有效，应在对应平台立即吊销并替换。

公众号 Secret、AES Key、数据库密码和 QQ 邮箱授权码全部通过环境变量或服务器密钥文件注入。生产 `.env` 权限应限制为部署用户可读。

## 验收标准

- 六类公众号事件均能通过模拟回调正确入库。
- 重复推送不会重复计数。
- 昨日统计在北京时间边界上准确。
- 每天 07:00 能生成并发送 QQ 邮箱日报。
- 空数据日期仍发送成功日报。
- 手动补发接口受密钥保护且能补发指定日期。
- 所有凭据均不进入代码、镜像层和 Git。
- Docker Compose 可启动完整服务并通过健康检查。
- dev2 部署配置经过只读环境检查后可使用。

## 协议与可靠性补充

本节是对前文的细化；如有歧义，以本节为准。

### 微信事件规范映射

回调路由为 `/wechat/callback/{appId}`。GET 成功时以 `text/plain` 原样返回 `echostr`；POST 完成入库或识别为重复事件后，在微信规定时间内返回字面值 `success`。

| 微信 MsgType/Event | 内部类型 | 规范字段 | 日报位置 |
| --- | --- | --- | --- |
| `event/subscribe` | `SUBSCRIBE` | 可选 QR Scene、Ticket | 关注；有 Scene 时也进入二维码明细 |
| `event/unsubscribe` | `UNSUBSCRIBE` | — | 取消关注 |
| `event/SCAN` | `SCAN` | QR Scene、Ticket | 二维码扫描 |
| `event/LOCATION` | `LOCATION` | 纬度、经度、精度 | 位置上报 |
| `event/CLICK` | `MENU_CLICK` | EventKey | 菜单拉取消息 |
| `event/VIEW` | `MENU_VIEW` | EventKey URL | 菜单跳转链接 |
| `event/其他已支持菜单事件` | `MENU_OTHER` | EventKey、原始事件名 | 自定义菜单其他事件 |
| 任意未识别值 | `UNKNOWN` | 原始 MsgType/Event | 未识别事件 |

“自定义菜单其他事件”不包含 `CLICK` 和 `VIEW`。支持的其他菜单事件采用白名单并固化为测试夹具；不在白名单中的值进入 `UNKNOWN`。

扫码关注的原始 `EventKey`（例如 `qrscene_campaign-a`）完整保存在 `raw_event_key`，规范场景字段只去掉开头的一个 `qrscene_`，得到 `campaign-a`。`SCAN` 的 EventKey 以相同规则规范化。空白值按缺失处理。这样同一场景不会在日报中分裂。

安全模式验签解密后必须验证消息接收公众号与路径对应的 `WECHAT_APP_ID` 相同。请求体上限 256 KiB；超限返回 413，格式错误返回 400，签名或 AppID 不匹配返回 403。XML 解析必须关闭 DTD、外部实体和外部 Schema，防止 XXE。无效 `msg_signature`、错误 AppID、损坏密文均不得进入持久化。

### 事件幂等的精确定义

有微信消息 ID 时，幂等键为 `msgid:<十进制消息ID>`。没有消息 ID 时，将以下字段按固定顺序，以 UTF-8、长度前缀和显式 null 标记规范序列化：

1. AppID
2. OpenID
3. 原始 MsgType
4. 原始 Event
5. 微信 CreateTime 的秒级整数
6. 原始 EventKey
7. Ticket
8. 纬度、经度和精度的规范十进制字符串

对序列化结果计算 SHA-256，存为 `sha256:<64位小写十六进制>`；数据库列为 `varchar(71)`，并与 AppID 组成唯一索引。

微信事件通常没有消息 ID，且 CreateTime 仅精确到秒。因此，同一用户在同一秒内产生字段完全相同的两个真实事件时无法和重试区分，系统会合并为一次，日报可能少计。这是上游载荷限制。不能加入接收时间规避，否则微信重试会被重复统计。

### 报告语义

Java 使用 `Instant`，MySQL 使用 UTC `timestamp(6)`，JDBC 会话时区显式设置为 UTC。应用在 `Asia/Shanghai` 下计算昨天的左右边界，再转换为 UTC Instant，使用左闭右开区间查询。

总事件数和总去重用户数包含 `UNKNOWN`。关注、取消关注和净增长使用事件数，相应行同时展示去重用户数。二维码场景、菜单 Key 和跳转 URL 的每个明细行都展示事件数和去重用户数。缺失维度统一显示为“（未提供）”。

以微信 CreateTime 决定事件所属日期。时间戳超出接收时间前后 30 天时标记异常，改用接收时间归档，并计入异常时间戳指标。日报首次生成时保存不可变 JSON 统计快照；迟到事件不会改写已发送快照。管理员只有显式要求“重新生成并补发”时，才会创建包含迟到事件的新快照版本。

### 日报投递状态

使用两张表：

- `daily_report` 保存报告日期、统计区间、数据截止时间、版本号、不可变 JSON 快照和创建时间。报告日期与版本号唯一。
- `report_delivery_attempt` 保存报告版本、触发类型、投递 ID、状态、收件人快照、尝试次数、认领时间、租约截止时间、完成时间和清洗后的失败摘要。

自动任务通过数据库条件更新原子认领投递记录。同一时刻只有一个实例获得有效租约。`SENDING` 超过 10 分钟视为失效，可被恢复任务重新认领。一次投递最多三次总尝试，即首次加两次重试；瞬时错误按 5 秒、30 秒退避，认证失败等永久错误不重试。

SMTP 无业务幂等能力。如果进程在 QQ SMTP 接受邮件后、写入 `SENT` 前崩溃，恢复后可能重复发送。因此系统提供至少一次投递，不承诺严格一次。邮件 `Message-ID` 和正文包含稳定的报告日期、快照版本及投递 ID，便于识别重复邮件。测试覆盖并发认领、过期租约恢复和这一崩溃窗口。

QQ SMTP 发件地址为 `MAIL_USERNAME`，显示名由 `MAIL_FROM_NAME` 配置。连接、读取和写入超时均为 10 秒。失败摘要仅保留异常分类及经白名单过滤、最多 500 字符的服务端信息，不含邮箱授权码、邮件正文或收件人全值。测试覆盖瞬时失败重试、永久失败不重试和状态迁移。

### 手动补发和端点隔离

手动接口为 `POST /internal/reports/{date}/send`，管理密钥仅通过 `X-Lumora-Admin-Key` 请求头传递。可选 JSON 字段 `regenerate` 和 `force` 默认均为 `false`。报告日期必须早于北京时间今天。

默认补发复用现有快照。`regenerate=true` 创建新快照版本；`force=true` 允许已有成功投递时新增可审计的投递记录，绝不覆盖旧记录。密钥使用常量时间比较，且不进入 URL 或日志。

公网反向代理只暴露 `/wechat/callback/`。`/internal/` 和除公开存活探针外的 Actuator 端点仅允许服务器本机或内网访问。本项目回调、统计和邮件功能不使用公众号 Secret，因此第一版不配置 `WECHAT_SECRET`。

### dev2 发布与验收

生产镜像使用 Git 提交或发布版本作为不可变标签。dev2 同时保留当前成功版本和上一成功版本。发布先启动候选容器并通过本机健康检查，再切换反向代理上游；公网验证失败时立即切回上一版本。普通的单服务 `docker compose up` 不视为具备回滚能力。

在提供生产回调域名和验收邮箱后，dev2 验收包括：

1. 公网 HTTPS 回调 GET 验证成功。
2. 签名正确的模拟 POST 能持久化，重复 POST 不增加计数。
3. QQ SMTP 发出带“部署验收”标记的测试邮件。
4. 调度器日志和运行配置显示下一次北京时间 07:00 执行。
5. MySQL 容器重启后事件和日报快照仍存在。
6. 公网无法访问 `/internal/` 和受保护 Actuator 端点。
7. 候选版本健康检查失败时，公网仍由上一成功版本服务。

模拟 POST 和 SMTP 冒烟会产生外部状态，只在部署操作者明确提供验收配置后执行。单元及集成测试还必须覆盖无效签名、错误 AppID、损坏密文、超限 XML、XXE、数据库故障导致微信可重试响应、QR 场景规范化、跨日边界和所有投递状态迁移。
